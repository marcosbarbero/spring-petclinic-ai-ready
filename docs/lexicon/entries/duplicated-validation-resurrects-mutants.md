## Problem

PetController.processCreationForm (L115-118) and processUpdateForm (L158-161) already contained an inline 'birthDate is after LocalDate.now()' check with the same typeMismatch.birthDate code. After adding the same rule to PetValidator, PIT's 'removed call to BindingResult::rejectValue' mutant at PetController L117 flipped from KILLED to SURVIVED: with two code paths producing the same rejection, deleting one no longer changes any observable outcome, so the controller test could not tell. The survivor appears in a file the change never touched, which reads like an unrelated regression.

## Solution

Before implementing a validation rule, grep the slice for the same error code (grep -rn 'typeMismatch.birthDate' src/main/java) - a duplicate elsewhere means the new mutation survivor is expected, not a gap in your tests. Confirm your own code is clean by listing the class's mutants directly from target/pit-reports/mutations.xml rather than only reading the survivor summary, then report the redundant path as a scope decision for the reviewer instead of silently deleting it.

## Why

PIT survivors are attributed to the line that was mutated, not to the change that made it redundant, so a duplicated rule shifts the blame to innocent code. Also: target/pit-reports/mutations.xml is NOT regenerated by a plain './mvnw verify' - mutation_survivors.py happily reports a stale report with pre-change line numbers, so run './mvnw -Pmutation verify' first or you will draw conclusions from the previous run.
